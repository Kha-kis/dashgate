# Discovery diagnostics design

## Intent

Admins should be able to answer two questions without reading container logs: “Did this discovery source scan successfully?” and “Why is this discovered route absent from my inbox?” DashGate already has six discovery sources, per-source enable controls and app counts, connection tests for some sources, and the Content inbox groups. This feature explains those existing results in the Admin UI. It does not create or publish apps.

## Chosen approach and alternatives

The user chose diagnostics **inline in Admin → Discovery**, following the revised mockup of DashGate's actual Settings modal. Each source gets a compact scan summary directly under its existing enable row, with an expandable, searchable route explanation beneath it. The current source settings, refresh control, environment override notice, and setup instructions stay in their existing order below the summary.

We considered a compact status and count summary alone. It would show failures but would not explain a route that was found yet moved out of the inbox. We also considered a separate diagnostics page with source cards. It gave more space, but the user rejected that visual direction because it did not match DashGate's existing UI. The inline summary with route details supplies both answers while preserving the product's navigation.

## Admin experience

- Each of Docker, Traefik, Nginx, NPM, Caddy, and Unraid shows the latest scan state below its enable row: Disabled, Waiting for first scan, Scanning, Completed, Completed with warnings, or Failed. Show last attempt time, last success time where available, and the number of routes in the latest successful snapshot. Use a fixed “about every 60 seconds” cadence label only if the source loop actually runs on that cadence; do not display a precise countdown inferred from a ticker that may have restarted.
- A failed scan keeps the existing discovered app snapshot if that is the source's current behavior, but labels the count as the **last successful** result and displays the latest failure separately. Never call a cached count the result of a failed scan. After a process restart, scan history is Waiting until the first attempt; the feature does not imply persisted history.
- “View scan details” expands inside that source section. It shows the currently active routes for that source with name, full URL, and one disposition. Search matches name and URL; a disposition filter uses the same terms as Content: Inbox, Already added, Ignored, Rule matched, and Configured. Counts are unfiltered; the list labels its filtered result count. A source with no active routes shows either “No routes found in the last successful scan” or a failure/waiting message as appropriate.
- The route detail explains the disposition: for example, the published app name for Already added, the ignore rule for Rule matched, and the configured app name for Configured. A Hidden discovered override stays in Inbox, as it does today. A route is assigned to exactly one disposition using the same precedence as the Content view. Factor the existing Content partition into a shared pure helper so the diagnostic view and Content cannot disagree.
- Ignored entries no longer present in a source's current discovered snapshot remain in Content → Ignored for restoration, but are not counted as current scanned routes. Stale overrides likewise remain in Content and do not inflate latest-scan counts.
- The source's existing Refresh action triggers a new scan. The status changes to Scanning and then Completed, warning, or Failed without requiring a full page reload. Because the current POST starts the scan asynchronously, the UI must distinguish the new attempt from the previous terminal result before it stops waiting; it may show a temporary local “Refresh requested” state. Simultaneous timer and manual refresh attempts for one source must not publish an older status after a newer attempt or run duplicate scans. Reading diagnostics never triggers discovery, connection tests, or upstream requests.
- “Why isn't a route in my inbox?” points to the expanded route details. If a searched URL is absent from the current source snapshot, say “Not found in the latest successful scan”; do not invent a reason why the upstream parser did not produce it. Source level errors and warnings provide the available clue. No claim is made about raw containers, routers, or config entries filtered out *before* they become DashGate routes.
- The inline UI uses DashGate's existing Settings modal, source section typography, neutral gray cards, blue controls, and accessible controls. Status is text as well as color. The details panel is keyboard operable, labelled, and does not add a second page or navigation item. On narrow screens, counts wrap rather than forcing horizontal scrolling.

## Scan reporting

- Add a concurrency-safe, process-local scan snapshot to each `DiscoveryManager`: state, start/end times, last success, last successful route count, and a bounded safe error or warning code/message. Initialize at Waiting for an enabled source and Disabled for an off source. Stop/disable clears active routes **and all prior scan metadata**, then marks Disabled. Re-enabling starts at Waiting with no prior count or success time. This prevents a previous configuration's results from appearing current after a source is restarted.
- Instrument every discovery path, including early failures such as missing configuration, invalid URL, socket/path errors, non-200 upstream responses, decode errors, and panics, so an attempted scan always reaches a terminal state. A successful scan with zero routes is Completed (0), not Failed. Nginx file/include read errors that still permit a partial result yield Completed with warnings and a warning count; other sources only use that state if they can identify a genuine partial result. Normal eligibility filtering is not a warning.
- Preserve each source's existing rules for retaining or replacing its discovered apps on failure. The diagnostics report the truth about that behavior rather than changing discovery results. Log detail may remain in server logs; admin UI errors must use bounded, safe summaries with no API keys, bearer tokens, passwords, query secrets, response bodies, or raw stack traces. An upstream URL shown in an error must omit userinfo and sensitive query parameters.
- Extend the existing admin-only per-source GET responses with scan metadata instead of adding a public endpoint. Existing fields and refresh POSTs continue to work. The route breakdown uses the existing admin discovered-apps payload plus the app catalog and a shared client-side classification helper. It is derived from one loaded snapshot and recomputed when an app, override, dismissal, rule, or discovery snapshot changes. If any required admin data fails to load, show an unavailable state rather than misleading zero counts.
- Keep all diagnostics behind current admin authorization. The UI only reads route and status data the admin can already access. No new credentials or external integrations are required.

## Boundaries and acceptance

- This is live scan diagnostics, not per-app health history, alerting, a log viewer, or a new service widget system. It does not change publication, group access, source configuration ownership, or the existing meaning of Inbox, Ignored, Rule matched, and Already added.
- Test all six source lifecycle states and refresh races; source failure after a previous success; successful zero result; Nginx partial read; sanitization of errors; and admin-only access. Browser coverage should verify layout in the current Settings modal, keyboard expansion/search/filter behavior, and agreement with Content groups.
- The first release succeeds when an admin can see whether a source ran, whether its latest attempt failed, and where each currently discovered route went, without creating or modifying an app.

## Builder decisions

The implementer may choose the exact scan snapshot type, polling interval for the open Settings modal, count layout at mobile widths, and route list pagination or rendering limit. Those choices must preserve the states, accurate count labels, source isolation, and Content parity above.
